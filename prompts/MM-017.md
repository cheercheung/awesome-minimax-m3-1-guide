# BAMBOO HOP pet flight

[Source](../sources/handbook.md#mm-017) · [Case 17](../README.md#case-17)

```text
请使用我提供的素材，直接制作一个完整、可运行、可反复游玩的网页游戏：《竹蜻蜓飞行队 / BAMBOO HOP》。完成项目文件、真实素材接入、交互逻辑、响应式布局和验证，交付可直接打开的游戏。
这是一款参考 Flappy Bird 的轻量飞行小游戏：玩家选择戴着竹蜻蜓的小猫或小狗，点击或按空格向上飞，穿过连续障碍，并收集罐头、猫粮、狗粮和冻干。气质可爱、轻松，动物保留原有的低模和照片贴图质感，背景与 UI 要协调。
1. 先检查素材，再开始实现
先解压并检查素材目录、manifest 和实际图片尺寸，处理好 ZIP 多包一层文件夹的情况。已有 8 位队员，编号为 01、02、03、06、10、11、12、16；对应橘猫吐司、三花饭团、奶牛芝麻、暹罗布丁、柯基奶盖、金毛豆包、腊肠可可、吉娃娃花生。全部开放选择，各自使用正确的图片和动画，物理能力相同。
选角卡片使用透明 PNG，大预览可使用动态 WebP，游戏中使用 PNG 精灵图。现有角色精灵图为 2048×1280，8 列×5 行，每格 256×256，共 40 帧，25 fps，按从左到右、再从上到下的顺序读取。核对实际文件后接入，每次只绘制一帧。
每帧已包含动物和竹蜻蜓，不再叠加第二个旋翼，不旋转整张精灵图。保持透明背景和动物比例；统一缓存图片，角色加载完成后才能进入准备页。
地图、障碍、食物图标、艺术字、音效和音乐优先使用提供的真实资产。图集按 manifest 的绝对裁切坐标读取。缺少某个必需素材时明确指出，不把占位图描述成已接入的素材。
2. 完整流程和 UI
流程为：首页 → 选择队员 → 选择地图 → 加载 → 准备起飞 → 游戏 → 结算。支持设置、暂停、继续、重开、更换地图、更换队员和返回首页。
首页使用提供的透明艺术字 PNG 显示游戏名，搭配动态队员、最高分、开始飞行和设置按钮。视觉使用奶油白、深绿、蜂蜜黄，按钮有清楚的层级、按下反馈和键盘焦点。避免把普通粗体文字当成最终主标题。
选角页显示全部 8 位队员，桌面有放大的动态预览与 4×2 卡片网格；手机压缩留白和预览尺寸，保证名字及操作按钮清楚可见。选中状态体现在卡片边框和底色，不用虚线圈或白色装饰盖住动物。
选图页展示 3 张地图的真实预览、名称、难度和各自的本地最高分。
准备页使用居中的起飞卡：桌面左侧放大展示当前动态队员，右侧排列“准备起飞”、地图、难度和黄色“开始飞行”按钮；手机改为上下排列。返回首页带文字和安全边距。操作提示只保留一处，背景不重复出现另一只动物。
游戏 HUD 只保留当前穿柱分、补给数量和暂停按钮。
结算显示本次分数、最高分、地图及各类补给数量，提供“再飞一次”“换张地图”“换个队员”“返回首页”。每个操作都是真实、可见的按钮；不显示“先歇一下……”等随机结算文案。
3. 电脑和手机都铺满可用画面
电脑以 16:9 横向构图为参考，手机以 9:16 竖向构图为参考。实际按浏览器可用窗口铺满，支持 16:10、超宽屏、手机长屏和横竖切换。Canvas、背景、HUD、菜单使用同一个舞台，不出现游戏只占中间一小块或两侧露出无关底色。
场景保持等比，背景用 cover 裁切，动物和障碍不拉宽、不压扁。逻辑世界高度固定 768，宽度按实际宽高比推导；横屏增加视野，不能改变重力、碰撞或障碍到达玩家的反应时间。UI 按可用空间重新排版，不把手机页面整体拉伸成电脑页。
处理设备像素比、手机安全区域和动态浏览器高度。正常游戏不滚动页面；极小窗口的菜单可内部滚动。调整窗口大小不清空分数或重开本局。
4. 飞行手感与连续障碍
玩家的水平位置基本固定，背景和障碍向左移动。每次有效点击、触摸或空格，将竖直速度设为一次固定向上速度；松开后受重力下落。长按不连发，拖动不能控制坐标。
以逻辑高度 768 为基准，使用初始参数：地面 y=704、角色初始 y=330、重力 980、起飞速度 -330、最大下落速度 560、角色显示尺寸 96×96。角色身体碰撞圆半径 20，绘制锚点为宽度的 55%、高度的 58%；透明留白、旋翼和尾巴尖不按整张图片矩形参与碰撞。触顶约束在画面内，撞地面或柱子结束游戏。
三张地图分别对应简单、普通、困难，沿用素材包的真实名称和美术：牧场、夕阳、夜景主题。按地图选择固定难度，不在一局中突然改变已有障碍。

柱子外宽 76。第一、第二对空隙靠近起始高度，给玩家适应时间；后续空隙在合法范围内平缓变化，只在创建时随机一次。
障碍必须按滚动距离持续补充：维护前方预加载距离，用循环补齐右侧队列，及时删除左侧离屏障碍，队列为空时能恢复。不能只创建开头两对，也不能依赖得分才生成下一对。扩宽窗口后补足前方障碍，已有柱子的世界位置保持不变。
障碍纹理、柱身、柱帽的可见轮廓与碰撞矩形一致。正确区分上柱和下柱的端帽，不出现柱帽突出、贴图接缝或碰撞框超出画面的情况。每通过一对障碍只加一分；同一步先检测碰撞，再处理拾取和得分。
5. 可吃的宠物补给
收集物使用提供的宠物食品资产：罐头、猫粮袋、狗粮袋、冻干。按当前队员种类显示猫粮或狗粮，罐头和冻干通用。
每对障碍最多关联一份补给，放在可安全通过的通道内；不嵌入柱子，不遮住下一处空隙。基础分布为粮食约 55%、冻干约 35%、罐头约 10%，每份记 1 个补给。物品类型创建后固定，收集只触发一次，离屏及时回收。
补给数量与穿柱得分分别统计。拾取有轻量动画和短音，结算按种类显示数量；没有任何物品时也能正常结算。
6. 音效与三张地图的音乐
接入我提供的短音效和三首 BGM，按素材配置一图一曲，整体为可爱、轻快的电子小游戏氛围。
每次有效起飞播放一次可爱的短音；拾取、得分、碰撞、菜单和结算有对应反馈。第一次真实操作后启用音频，起飞按钮不同时叠加两次音效。长按不连续播放，迟到的加载请求不能在暂停后补播一串旧声音。
同一时刻只播放一条 BGM。开始游戏时播放对应地图曲目；暂停记住播放位置，继续恢复；死亡或返回菜单停止，重开从头开始，切地图切换曲目。音乐播放完可重播，不把整首歌曲循环描述成已制作无缝接点。
设置里提供独立的音效开关、音乐开关及各自音量，并保存设置。音乐使用适合长音频的播放器，避免一次把三首整曲全部解码到内存。音频失败不阻断游戏。
7. 状态、输入和稳定性
用明确状态管理 HOME、SELECT、MAP_SELECT、LOADING、READY、RUNNING、PAUSED、DYING、GAME_OVER，所有页面按钮接通。
READY 中角色只悬停，不受重力、不计分。第一次有效输入同时开始游戏和触发一次起飞。准备页点背景、点卡片、点起飞按钮或按空格均可开始；返回、设置、暂停等按钮只执行自身操作。统一指针输入，防止一次触摸被 pointerdown、touch 和 click 重复处理；忽略空格自动重复。
项目只启动一个 requestAnimationFrame 主循环，固定物理步长并限制异常帧间隔。暂停时物理、障碍和游戏动画时钟冻结；切后台自动暂停，回来由玩家主动继续。清理隐藏菜单的旧焦点，避免继续游戏后空格失效。
死亡只结算一次。重开清空分数、补给、障碍队列、已得分标记、速度、计时、粒子和待处理输入，保留选中的队员和地图，回到准备页。不能重复注册监听或让游戏越重开越快。
使用本地存储保存最高分、分地图记录、上次队员/地图和设置；损坏或不可用时回退到默认值。快速换角色或地图时，旧异步加载结果不能覆盖新选择。
8. 技术和交付
采用 HTML、CSS、原生 JavaScript 与 Canvas 2D，UI 可用 DOM 实现。无需后端、账号、API Key 或外部 CDN。资源使用相对路径；素材配置可以整理为本地 JS，不能依赖 file:// 下容易失败的 JSON fetch 才能启动。
交付完整项目目录与 ZIP，包含真正使用的全部素材、README、端口 6817 的 start-local.sh、macOS start-local.command 和 Windows start-local.bat。启动脚本先进入项目目录，端口被占用时提示，不结束其他进程。
同时提供可双击打开的独立 HTML，由源码自动构建，真正内嵌所需图片、CSS 背景、脚本、音效和三首音乐。把单 HTML 复制到空目录也应能运行；不能只有资产名称或清单，实际仍偷偷请求原文件。
9. 完成后实际验证再交付
至少检查：8 位队员分别进入游戏、3 张地图切换、旋翼动画、第一次起飞、连续障碍、碰撞和计分、四类补给显示、暂停/后台恢复、连续重开 5 次、菜单按钮误触、音效和 BGM 生命周期，以及刷新后保存恢复。
独立验证每张地图的障碍流连续运行至少 3 分钟，不在开头两对之后断掉；实际游玩检查保持正常重力、碰撞和真实计分。桌面 1920×1080、1440×900 和手机 390×844、360×640 下检查首页、选角、选图、准备、游戏、结算和设置，确认没有遮挡、拉伸或裁掉按钮。
确认没有资源 404、控制台未处理错误、图片错帧、音乐重叠和移动端一次触摸跳两次。发现问题直接修复，并在交付中简短说明实际完成的验证；没有真实浏览器能力就如实标明，不能把模拟 DOM 测试写成实机验收。
现在开始检查素材并实施，持续完成到可以交付完整游戏。未写明的小细节选择与现有美术一致的稳妥方案。
```
